**What is worth preserving**

The product has a coherent purpose: get existing friends into a private game quickly. The felt, lacquer, ivory, and brass clubhouse identity supports that purpose. The server uses cryptographic shuffling, personalized views, schema validation on room/game inputs, distinct production secrets, account checks, and disabled-by-default purchases. Referral credits use a serializable transaction and unique ledger keys. The container runs as a non-root user; CI provisions PostgreSQL and includes mobile export; the runbook acknowledges the single-replica constraint. These are useful foundations, but they do not establish end-to-end game correctness.

**Release-blocking findings**

P1 below means fix before expanding the beta. Severity is based on reachable behavior in this social-play application, not hypothetical cash exposure.

1. **P1 — The authoritative evaluator can award the pot to the wrong hand.** [handRanking.ts:66](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/handRanking.ts:66) separates categories by 1,000, while the rank-specific contribution can exceed 1,000. A-K-J high card scores above a pair of twos; A-K-J of one suit scores above a 4-5-6 sequence. Base-10 weighting also cannot safely represent ranks up to 14 as independent tie-break positions. Replace scalar comparison with a lexicographic category/tie-break tuple; keep AI confidence scores separate. Enumerate all 22,100 three-card combinations to verify category boundaries, then test ordering, ties, and the documented lowball rules. Existing tests pass despite these examples.

2. **P1 — Server timeouts cannot execute.** [gameEngine.ts:300](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/gameEngine.ts:300) requires membership in `getAvailableActions`, which never includes `timeout`. [roomManager.ts:362](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/roomManager.ts:362) submits that action, catches its failure, and schedules no replacement. A disconnected or inactive current player can stall the table. Separate internal timeout commands from player commands and guard them with the expected hand/turn version. Test actual elapsed timers; the existing disconnect test manually sets a player to folded rather than exercising timeout resolution.

3. **P1 — Quick-play bots cannot submit actions.** [roomManager.ts:195](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/roomManager.ts:195) inserts bots into `room.players`, but only human `joinRoom` calls populate `playerRooms`. The AI callback calls `handleAction(botId, ...)`, which returns `Not in a room`. Bot turns have no human timeout fallback. Use a room-scoped internal command path for bots; globally mapping the reused bot IDs would introduce cross-room collisions. Require complete AI games and simultaneous independent quick-play tables to pass.

4. **P1 — Seeing cards does not end blind status.** [gameEngine.ts:551](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/gameEngine.ts:551) sends the viewer their cards and evaluated result even while blind. Web/mobile “See Cards” only toggles local visibility. Players can inspect the hand and continue using blind actions/pricing. Introduce an irreversible server `see_cards` action; do not disclose cards or hand strength until it succeeds. Hiding cards again must not restore blind status. Test payloads, not just visual concealment.

5. **P1 — Supplied bet amounts bypass game rules.** [gameEngine.ts:318](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/gameEngine.ts:318) accepts supplied blind/chaal/raise amounts after checking only available chips. A valid socket request can wager 1 against a current bet of 50; a small raise can lower the reference bet. The room schema also permits a boot greater than the buy-in, producing a negative initial stack. Derive valid ranges from authoritative state and validate both room configuration and every action. Decide and implement the intended short-stack policy: the UI offers “All in,” but the engine never transitions into `all_in` or resolves contribution-based pots. Until supported, do not offer that action.

6. **P1 — Socket operations can leave clients waiting indefinitely.** [mobile socket.ts:40](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/packages/mobile/src/services/socket.ts:40) always emits `(event, data, callback)`, even with undefined data. The server's `room:list` and `game:quick_play` handlers expect the callback as the first argument. The safety wrapper makes the misplaced argument a no-op, so these mobile promises never resolve. Both clients also lack acknowledgement deadlines. Separately, [web socket.ts:94](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/packages/web/src/services/socket.ts:94) waits for ten connection errors; middleware rejection does not automatically reconnect, so the first rejected connection can leave its promise pending. Fix argument shape, settle every promise, refresh/re-authenticate deliberately, and clean up replaced sockets. Socket.IO documents [middleware rejection behavior](https://socket.io/docs/v4/client-socket-instance/#connect_error) and [acknowledgement timeouts](https://socket.io/docs/v4/client-options/#acktimeout). Automatic command retries need idempotency keys first.

7. **P1 — A waiting-table leave does not reach the server on web.** [gameStore.ts:83](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/packages/web/src/stores/gameStore.ts:83) emits `room:leave` only when `isOnlineMode` is true; that flag is set on the first game state, not the waiting room state. A host can leave an unstarted table locally while remaining seated on the server. Later creation can report success even though `joinRoom` fails because the player still belongs to the first room. Always acknowledge server membership changes; creation plus admission must succeed or roll back together. Test create → leave before a friend arrives → create another table.

8. **P1 — The friend-table lifecycle is incomplete.** [roomManager.ts:126](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/roomManager.ts:126) refuses joins during play, while the second player triggers an immediate deal. Later invitees cannot join an ordinary six-person game already underway. After a hand, [roomManager.ts:489](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/roomManager.ts:489) emits `game:ready_for_next`, but no server ready/start-next handler exists and the web hook does not handle that event. The UI returns players to the lobby. Add explicit waiting, ready, playing, settling, and between-hands states; admit late friends for the next hand; preserve table identity and final stacks. Acceptance: three friends arrive at different times, play three consecutive hands, and one reconnects without losing their seat.

9. **P1 — Settlement failures can be discarded.** [roomManager.ts:402](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/roomManager.ts:402) catches persistence failure, still announces the outcome, then clears the only game state after five seconds. There is no persisted settlement job or retry. The schema has a useful unique transaction reference, but no durable record drives recovery. Leaving also removes room membership without folding/removing the player from the active hand, permitting another room while prior exposure is unresolved. Buy-in checks do not reserve a balance, and room stacks are not synchronized with final game stacks. Introduce reserved table balances, durable hand results, idempotent settlement, and recovery for pending settlements; define leave/deletion behavior during a hand. Test database interruption, process restart, duplicate delivery, and leave/rejoin before settlement. A single-replica policy alone does not solve restart recovery.

10. **P1 — Daily rewards have a concurrent double-claim path.** [users.ts:324](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/routes/users.ts:324) reads the previous claim outside the transaction. The schema uniqueness is `(userId, claimedAt)`, not `(userId, rewardDay)`, so requests with different timestamps can both pass the precheck. Ledger balances are also written as zero. Use an explicit UTC reward date with a unique user/day constraint and a transaction that records the actual balance movement. Confirm under concurrent PostgreSQL requests; this audit established the source-level race but did not run a database reproduction.

11. **P1 — Offered variants do not use their variant machinery.** [gameEngine.ts:100](/Users/durjoy/Documents/TeenPatti/social-teen-patti-impeccable/server/src/game/gameEngine.ts:100) always deals three cards from a normal deck. Joker/AK47 preparation, trump selection, and Best of Four helpers exist in `variants.ts` but are not called by the active engine. The active evaluator only specializes Muflis/Lowball. Web room creation visibly offers Joker and AK47. Gate unsupported variants off server-side and in the UI, then enable each against a published, tested ruleset. “Best of Four deals three cards” was reproduced locally.

**Architecture to aim for**

Keep the monorepo and the current deployment model while correcting responsibilities. A framework rewrite or microservices split is not justified by the evidence.

| Boundary | Responsibility |
|---|---|
| Shared rules | One canonical rules/evaluator implementation, deterministic state transitions, explicit variant policy, chip arithmetic, and invariants. Inject server randomness and time; never send private deck state to clients. |
| Shared protocol | Runtime schemas and TypeScript event types for commands, acknowledgements, snapshots, deadlines, and errors. Include hand ID, command ID, and expected state version. |
| Room coordinator | Serialize commands per table, own seats/readiness/disconnect deadlines, invoke the rules engine, reject stale commands, and produce durable transitions. |
| Persistence/economy | Reserve stacks, record hands/results, settle exactly once, maintain auditable balances, and enqueue referral/notification work transactionally. |
| Web/mobile | Present the same authoritative view model, identify the viewer explicitly, show recovery states, and apply shared error/ack behavior. |
| Operations | Restore/drain procedures, release gates, per-table diagnostics, alerts, and load tests against an explicit expected traffic envelope. |

There are currently separate server, web, and shared game implementations, plus duplicated i18n/economy code. Centralization should follow correctness fixes with characterization tests; blindly moving current rules into shared code would spread the bugs. Keep transport adapters separate from pure game logic. Before multiple replicas, define room ownership and fencing; a pub/sub adapter by itself cannot make mutable in-memory room state safe.

**How to make the experience exceptional**

The strongest positioning is a dependable private card room for friends. Make the full social evening work: share a link, see who arrived, wait for the group, play several hands, reconnect, and return to the same circle later.

Preserve the clubhouse materials and typography. In the stored mobile screenshot, the decorative table dominates nearly the entire viewport and the share button sits at the lower edge. Test compact-height phones and larger text, and keep the next action visible without needing to understand the decorative seat map. The desktop layout can use its utility panel for actual attendees, readiness, invite status, and recovery actions. Current room snapshots are reduced largely to counts in the lobby; retain actual member identities and presence for the seats.

Make game information effortless: an unambiguous blind/seen state, exact action cost, a server-backed countdown, the last accepted action, and a post-hand explanation of why each winner won. Present each winner's actual split payout rather than the entire pot for every winner. Provide a one-tap next hand, late-join seats, and a clearly stated leave consequence. Keep onboarding skippable or contextual for invitees so their friends are not waiting through a separate lesson.

Finish accessibility across the complete journey. The create/join dialogs already implement focus handling, so build on that. Test keyboard-only play, screen readers, focus restoration, modal background isolation, color-independent suit recognition, dynamic text, and reduced motion including persistent animations. Follow the [W3C dialog interaction pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). Avoid treating a few ARIA attributes or a reduced-motion toggle as comprehensive verification.

Use one design token source for web/mobile and migrate hard-coded utility colors gradually. The active web journey contains substantial hard-coded English despite multiple locale files. Complete localization for the shipped journey, including game vocabulary, error recovery, dates, and readable scripts, before promising language coverage. Remove dormant experiments from production import paths or clearly isolate them as prototypes.

| 4 — Product finish | Consistent tokens, accessible gameplay, live preferences, localization, working equipped cosmetics | Keyboard/screen-reader/large-text checks; every visible action changes real state and persists as intended |
| 5 — Measured beta | Full journey CI, load/fault tests, support tools, operational dashboards and release evidence | Known traffic envelope, alerts exercised, restore rehearsal, current dependency results, and no unresolved P1 findings |

These stages are dependency order, not delivery estimates. Estimate them after agreeing the rules and the intended room/stack lifecycle.

The current CI tests helpers and rankings, but has no web/mobile interaction suite. The production smoke script stops after joining a table; it does not finish a hand, verify settlement, or redeem/equip a reward. Add a small high-value end-to-end suite around those outcomes instead of chasing a line-coverage percentage. Include adversarial input and property tests for chip conservation, monotonic state versions, legal winners, and terminal-state immutability. Retain fast unit tests and PostgreSQL concurrency tests separately.

Proposed quality targets—not measurements from this audit—are p75 LCP ≤2.5s, INP ≤200ms, CLS ≤0.1, plus product-specific budgets for command acknowledgement and reconnect restoration. The web thresholds follow [Core Web Vitals guidance](https://web.dev/articles/vitals). Measure mobile hardware, a realistic regional network, background/resume, and long sessions before choosing game latency SLOs.

Measure the social promise using server-confirmed events: share/open → successful seat → first completed human hand → second hand → same group returns. Track hand completion rate, reconnect recovery, unresolved settlement count, and support incidents alongside retention. Client analytics currently emit a completed-game event before database persistence is necessarily successful; use backend settlement as the source of truth for completion and rewards. Establish baselines before assigning growth targets.

**Recommended next investment:** repair and prove the classic private-table journey, with a complete replay and recovery loop. The visual identity is already a useful asset. Reliable outcomes, transparent rules, and continuity between friends are the improvements most likely to turn this prototype into a product people trust and return to.
